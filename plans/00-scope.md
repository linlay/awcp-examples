# 范围与验收约定

## 初始交付记录

最初交付项目目录、无页面骨架、Core AWCP 接入和任务拆分，当时没有实现业务页面或安装依赖。用户随后准备了依赖并要求按计划实施项目；B00～B03 已完成，结果见 [B01 验收记录](../docs/baseline-verification.md)、[B02 路由说明](../docs/scenario-routing.md)及 [B03 数据说明](../docs/demo-data.md)。

## 完整项目目标

- 16 类通用办公，48 个独立任务；详情见 O01～O16。
- 5 条证券业务流程；S01～S03 先行，S04～S05 为完整版必做。
- 10 类协议实验，展示正常行为、错误和恢复。
- 共用场景目录、调试面板、虚构数据、角色、审批状态机、业务审计与可回放脚本。

所有业务页面的核心操作必须同时具备人工入口和 AWCP 操作链。静态页面、仅改参数的样例不重复计数。完整办公覆盖要求 48/48；首个演示里程碑不能宣称已经完成全部办公覆盖。

## 架构边界

React 18 + TypeScript strict + Webpack/SWC。Core 位于同级 CDK，以公共导出接入；应用页面与业务 service 分层。当前只引入 Core、React 与工程工具，后续组件、路由和 E2E 工具按具体任务添加精确依赖。

AWCP 使用 manual 两层发现和 Schema 运行时校验；不使用旧 snapshot 方案，不虚构 outputSchema、permission 或 requiresConfirmation 注册字段。单页 Action 工程目标不超过 40，协议硬上限为 128。

业务版本、事务、幂等、状态机与角色检查由 service 负责；revision 与 requestId 不替代这些机制。异步任务区分已受理与已完成，取消不代表回滚，未知结果先查询状态。

## 数据与外部服务

采用虚构证券公司、固定种子和模拟时钟；员工、部门、客户、文件、审批及待办使用共享 ID。邮件、邀请和研报发布写入模拟业务记录，不自动调用外部服务。HTTP 接入留在 service，实际需要时按中后台规范使用 Core HttpClient 和 180000ms 超时。

Office 原生文件完整编辑、实时行情、真实交易、生产后台、真实邮件和模型代理不在当前实现范围。证券流程是教学设计，规则必须标注为演示配置，不能将简化逻辑表述为机构的完整合规判断。

## 每项任务的完成定义

1. 页面、service、合同、数据和说明齐备。
2. 人工与 AWCP 操作从相同种子得到一致业务结果。
3. 经真实目录、章节与 invoke 完成操作，并核查实际记录。
4. 成功、字段失败、业务失败和适用的恢复路径有验证。
5. 页面切换清理 Action，普通数据变化不造成无意义的合同版本变化。
6. lint、typecheck、测试和 build 按阶段通过；没有执行的检查明确标记。
7. 清理临时文件、配置与测试数据，保留用户既有状态。

确定性 E2E 与模型任务评测分别报告。后者记录模型、宿主、任务、种子和重复次数，在试点后再约定成功率门槛。
